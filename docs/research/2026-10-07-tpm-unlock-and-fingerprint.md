# TPM2 LUKS auto-unlock and BF63112 fingerprint on the OneXPlayer 3 (CachyOS)

Date: 2026-10-07. Device: ONE-NETBOOK ONEXPLAYER 3, AMI BIOS 5.09, Intel Panther Lake, CachyOS, kernel `7.2.9-1-cachyos-deckify`.
All device facts below come from read-only commands run over ssh on 2026-10-07. Nothing on the device was changed.
Man-page quotes are from the **systemd 262** pages installed on the device and on the dev host. Upstream copies are at man.archlinux.org, which currently renders systemd 262.

---

## 0. URGENT: the root filesystem died during this research (NVMe s2idle bug)

This is unrelated to TPM or fingerprint work, but it blocks both and must be fixed first.

- **What happened.** At uptime ~1077 s (≈19:48 local), the device entered s2idle on its own: `PM: suspend entry (s2idle)`, after an idle `wlan0: deauthenticating … by local choice`.
- **Resume failure.** On resume the kernel logged `nvme nvme0: Disabling device after reset failure: -19`. Btrfs then aborted transaction 108, forced read-only, and has kept failing reads (`errs: wr 38, rd 810+`). Every uncached file read on the device now returns `Input/output error`. This includes `cryptsetup luksDump`, which reported "not a valid LUKS device".
- **Cause.** The SSD is a **Predator SSD GM7 1TB** (`1dee:1602`, fw `BM345CVN`), read from `/sys/class/nvme/nvme0/{model,firmware_rev}` and the PCI IDs.
  - At boot, the kernel logs `platform quirk: setting simple suspend`, so it takes the ACPI StorageD3Enable path.
  - That path is skipped by the `nvme.noacpi` module parameter ("disable acpi bios quirks"): see `noacpi` and the `acpi_storage_d3()` check in [drivers/nvme/host/pci.c](https://github.com/torvalds/linux/blob/master/drivers/nvme/host/pci.c).
- **Same bug as the community repo.** The community OXP3 repo documents exactly this SSD, firmware and error string. It reproduced the bug 7/7 times and fixed it with `nvme.noacpi=1`:
  - [README "Game-mode suspend/resume freeze"](https://github.com/HHHHanasak1/onexplayer3-steamos-setup/blob/main/README.md)
  - [issues/04-one-netbook-firmware.md](https://github.com/HHHHanasak1/onexplayer3-steamos-setup/blob/main/issues/04-one-netbook-firmware.md)
  - Confidence: high.
- **Action for the user.**
  1. Hard-reboot the device. The current boot cannot recover.
  2. Run `btrfs check --readonly` / scrub after boot.
  3. Add `nvme.noacpi=1` to the kernel command line **before** any LUKS header work, so that a mid-write NVMe drop cannot interrupt `systemd-cryptenroll`.
- **Where the parameter goes on CachyOS.**
  - systemd-boot entries are regenerated by `sdboot-manage` from `LINUX_OPTIONS` in `/etc/sdboot-manage.conf` (currently `"nowatchdog quiet splash"`). The entry's `rd.luks.name=…` is auto-generated from the mkinitcpio HOOKS ([sdboot-manage source](https://github.com/CachyOS/CachyOS-PKGBUILDS/blob/master/systemd-boot-manager/sdboot-manage), lines ~151–200).
  - So put `nvme.noacpi=1` in `LINUX_OPTIONS` and run `sdboot-manage gen`.
  - Also add it to `/etc/kernel/cmdline` if you later move to a UKI.
  - Hand-editing `/boot/loader/entries/*.conf` is overwritten because `OVERWRITE_EXISTING="yes"` is set.
  - Also wrap enrolment in `systemd-inhibit --what=sleep:idle:handle-lid-switch …`.

## A. TPM2 LUKS auto-unlock

### A.0 Current state (evidence)

- **`/proc/cmdline`:** `root=UUID=<root-uuid> rw rootflags=subvol=/@ rd.luks.name=<luks-uuid>=luks-<luks-uuid> nowatchdog quiet splash`
- **systemd versions:** userspace `systemd 262-1`. The ESP still has **systemd-boot 261.1**, per `bootctl status`. There is no `.efi.signed` file and Secure Boot is disabled.
- **`/etc/crypttab`** already has `luks-<luks-uuid> UUID=<luks-uuid> none` with no options. There is no `/etc/crypttab.initramfs`.
- **LUKS2 header** (read before the disk failed): one keyslot (0, argon2id), **no tokens**.
- **TPM:** `systemd-cryptenroll --tpm2-device=list` shows `/dev/tpmrm0 MSFT0101:00 tpm_crb_acpi`.
  - `systemd-analyze has-tpm2` returns `yes`, with `+firmware +driver +system +subsystem +libraries`.
  - `systemd-pcrlock is-supported` returns `yes`.
  - Only a `pcr-sha256` bank is exposed.
- **PCRs** (`systemd-analyze pcrs`):
  - PCR 7 = `4a772d24…`
  - PCR 9 (initrd) and PCR 12 (cmdline) are non-zero: the kernel measures the initrd, and sd-boot measures the cmdline.
  - PCR 11 = 0 (no UKI) and PCR 15 = 0.
  - `bootctl status`: `Measured UKI: no`.
- **Initramfs** (`lsinitcpio`) already contains:
  - `usr/lib/cryptsetup/libcryptsetup-token-systemd-tpm2.so`
  - `usr/lib/libtss2-{esys,mu,rc,sys,tctildr,tcti-device,…}.so*`
  - `systemd-tpm2-setup-early.service`
  - `usr/lib/nvpcr/cryptsetup.nvpcr`
- **Stale EFI variable:** `bootctl status` reports `Default Entry: onexplayer3-cachyos.efi`, but `/boot/EFI/Linux/` is empty, so systemd-boot falls back to `@saved`/first entry. There is also a `/boot/<machine-id>/7.2.9-1-cachyos-deckify/{linux,initrd}` kernel-install tree with no matching entry. Both look like leftovers; clean them up when moving to a UKI.

### A.1 What is needed for this stack

1. **Kernel modules and libraries: nothing to add.**
   - TPM drivers are built in: `CONFIG_TCG_TPM=y`, `CONFIG_TCG_CRB=y`, `CONFIG_TCG_TIS=y` from `/proc/config.gz`. `sd-encrypt` also runs `add_checked_modules '/drivers/char/tpm/'`.
   - mkinitcpio's `systemd` hook adds the dlopen()ed `tss2-{esys,rc,mu,tcti-*}` libraries ([install/systemd](https://gitlab.archlinux.org/archlinux/mkinitcpio/mkinitcpio/-/blob/master/install/systemd), the "add libraries dlopen()ed" loop).
   - `sd-encrypt` adds `libcryptsetup-token-systemd-tpm2.so` ([install/sd-encrypt](https://gitlab.archlinux.org/archlinux/mkinitcpio/mkinitcpio/-/blob/master/install/sd-encrypt)).
   - Do **not** add `tpm_crb` to `MODULES=()`.
2. **crypttab vs kernel cmdline.**
   - **Preferred: `/etc/crypttab` with `x-initrd.attach`.**
     - Since mkinitcpio commit [82e61a82 (2026-08-11, "prefer /etc/crypttab with x-initrd.attach over /etc/crypttab.initramfs")](https://gitlab.archlinux.org/archlinux/mkinitcpio/mkinitcpio/-/commit/82e61a82321ce69f00846716806d654ec9399260), first shipped in v41.1, `sd-encrypt` copies every `/etc/crypttab` line whose 4th field contains `x-initrd.attach` into the initramfs.
     - `/etc/crypttab.initramfs` still works but now prints a deprecation warning. The device runs mkinitcpio 42.2.
     - crypttab(5) also recommends `x-initrd.attach` for the root device, so that systemd does not try to detach it at shutdown while still in use ([crypttab(5)](https://man.archlinux.org/man/crypttab.5)).
     - The kernel cmdline keeps `rd.luks.name=<uuid>=<name>`, which sdboot-manage generates. systemd-cryptsetup-generator(8) says: "If /etc/crypttab contains entries with the same UUID, then the name, keyfile and options specified there will be used" ([systemd-cryptsetup-generator(8)](https://man.archlinux.org/man/systemd-cryptsetup-generator.8)).
     - The match accepts a device field of the form `UUID=…` ([cryptsetup-generator.c v262, ~L803](https://github.com/systemd/systemd/blob/v262/src/cryptsetup/cryptsetup-generator.c)).
   - **Alternative: `rd.luks.options=<luks-uuid>=tpm2-device=auto,tpm2-measure-pcr=yes`.**
     - On CachyOS this has to go into `LINUX_OPTIONS` in `/etc/sdboot-manage.conf`, because the entries are regenerated.
     - It "will override the options for the given UUID" (same man page).
     - This works, but it splits configuration across two tools and gets lost if you move to a UKI without copying it into `/etc/kernel/cmdline`. It is not recommended.
3. **Regenerate** with `mkinitcpio -P`. CachyOS uses the preset `/etc/mkinitcpio.d/linux-cachyos-deckify.preset` (default image only).
   - Verify with: `lsinitcpio -x`, or `lsinitcpio /boot/initramfs-linux-cachyos-deckify.img | grep etc/crypttab`.

### A.2 PCR policy

The PCR meanings below are from the table in [systemd-cryptenroll(1)](https://man.archlinux.org/man/systemd-cryptenroll.1) and the [UAPI.7 PCR registry](https://uapi-group.org/specifications/specs/linux_tpm_pcr_registry/):
- PCR 7 changes "when UEFI SecureBoot mode is enabled/disabled, or firmware certificates (PK, KEK, db, dbx, …) changes".
- PCR 9 holds all initrds measured by the kernel.
- PCR 11 holds the UKI as measured by systemd-stub, plus the boot phases.
- PCR 12 holds the kernel cmdline.
- PCR 15 holds the volume key when `tpm2-measure-pcr=` is set, plus machine-id and filesystem measurements.

The man page's guidance: "In general, encrypted volumes would be bound to some combination of PCRs 7, 11, and 14 (if shim/MOK is used)… it is typically not advisable to use PCRs such as 0 and 2". Note that `--tpm2-pcrs=` **defaults to no PCRs at all** (same page).

| Option | Kernel/initramfs update | What it protects against | Lockout triggers | Verdict |
|---|---|---|---|---|
| **PCR 7 only, SB off** | unaffected | SSD removed and read elsewhere. **Not** device theft: with SB off, PCR 7 only records SB state and key DBs, so a USB live system or a modified initramfs on the unencrypted vfat ESP sees the same PCR 7 and can unseal. The "filesystem-confusion" attack also applies ([oddlama, 2025-01-16](https://oddlama.org/blog/bypassing-disk-encryption-with-tpm2-unlock/)). | BIOS update or reset of keys, dbx update (fwupd), SB toggle | Convenience only |
| **PCR 7 + 15=0 (`tpm2-measure-pcr=yes`), SB off** | unaffected | Same as above, plus a fake root volume cannot unseal after the initrd has unlocked anything. This closes the oddlama attack only where the initrd itself is trusted, which is not the case with SB off. | as above | **Phase 1 (now)** |
| PCR 4+7+9+12, SB off | **breaks on every kernel or mkinitcpio run** (PCR 4 kernel PE, PCR 9 initrd, PCR 12 cmdline); new values cannot be pre-sealed without pcrlock | tampering with sd-boot, kernel, initrd or cmdline | every update → passphrase at next boot | Not suitable for a frequently updated handheld |
| systemd-pcrlock (v262) | predicted (`lock-pe`, `lock-kernel-initrd`, `lock-kernel-cmdline`, …) | strong | prediction gaps → passphrase | **Skip for now.** The man page says "this command is experimental for now". The policy reaches the initrd as a credential "picked up at boot by systemd-stub", so it effectively needs a UKI ([systemd-pcrlock(8)](https://man.archlinux.org/man/systemd-pcrlock.8)). |
| **SB on (own keys) + signed UKI, PCR 7 + 15=0** | unaffected (PCR 7 records the *authority*, your db cert, not the hash) | Only binaries signed by your db key boot without changing PCR 7. With SB on and an embedded `.cmdline`, systemd-stub ignores cmdline overrides ([systemd-stub(7)](https://man.archlinux.org/man/systemd-stub.7)). The initrd is inside the signed UKI, so it cannot be swapped. PCR 15=0 closes the fake-root attack. | key enrolment changes, dbx updates | **Phase 2 (target)** |
| + signed PCR 11 policy (ukify `[PCRSignature:initrd]` + `--tpm2-public-key`) | unaffected; the signature ships in the UKI | Binds to *your* UKIs and boot phase (`enter-initrd`), not merely "signed by db" | none from updates | Optional hardening ([ukify(1)](https://man.archlinux.org/man/ukify.1), [systemd-cryptenroll(1)](https://man.archlinux.org/man/systemd-cryptenroll.1) `--tpm2-public-key*`) |

Why a Type #1 entry is not enough even with Secure Boot on: systemd-boot loads `vmlinuz` through the firmware, so the kernel is verified, but `initramfs-*.img` on the vfat ESP is **not** signature-checked. An attacker can replace it and PCR 7 is unchanged. You need a UKI, or you must also bind PCR 9, which breaks on every mkinitcpio run.

**Lockout risk with SB off is low.** PCR 7 rarely changes, and any failure only falls back to the passphrase prompt. Data is never lost as long as the passphrase and recovery key slots are kept. The cases to plan for:
- **Turning SB on in Phase 2** changes PCR 7. Expect one passphrase boot, then re-run the script.
- **Firmware updates and fwupd dbx updates** also change PCR 7. Same handling.

**Secure Boot on CachyOS.**
- The [CachyOS Secure Boot wiki (updated 2026-08-25)](https://wiki.cachyos.org/configuration/secure_boot_setup/) supports systemd-boot via `sbctl`:
  - `sbctl create-keys`, then `sbctl enroll-keys --microsoft` (the wiki adds `--firmware-builtin` except on ASUS/Gigabyte).
  - `sbctl-batch-sign`, a CachyOS helper.
  - Caveat from the wiki: "The sbctl pacman hook will not sign the updated EFI binaries" for systemd-boot. Sign `/usr/lib/systemd/boot/efi/systemd-bootx64.efi` manually.
- bootctl prefers `systemd-bootx64.efi.signed` when present ([bootctl(1) "Signed .efi files"](https://man.archlinux.org/man/bootctl.1)). So register `sbctl sign -s -o /usr/lib/systemd/boot/efi/systemd-bootx64.efi.signed /usr/lib/systemd/boot/efi/systemd-bootx64.efi`.
- sbctl's `ZZ-sbctl.hook` re-signs registered files on `usr/lib/**/efi/*.efi*` changes, and its mkinitcpio post hook signs the UKI passed as `$3` ([ZZ-sbctl.hook](https://github.com/Foxboron/sbctl/blob/master/contrib/pacman/ZZ-sbctl.hook), [contrib/mkinitcpio/sbctl](https://github.com/Foxboron/sbctl/blob/master/contrib/mkinitcpio/sbctl)).
- mkinitcpio builds UKIs with `ukify` when it is installed, and reads `/etc/kernel/uki.conf`. That file is where `[PCRSignature:…]` keys would go (see `/usr/bin/mkinitcpio`, "Using ukify to build UKI").
- Enrolling the Microsoft keys (`-m`) is safe for TPM purposes. A Microsoft-signed binary is recorded with a different authority in PCR 7, so it cannot unseal.
- Unknown: whether the OXP3 AMI setup exposes "Reset to Setup Mode" or "Clear Secure Boot keys". See Open questions.

**TPM2 PIN.**
- `--tpm2-with-pin=yes|no|direct`. In v262, `yes` hardens the PIN with Argon2id, "making the TPM a second factor rather than a single point of failure"; `direct` is the v253-compatible PBKDF2 mode.
- Wrong PINs count toward the TPM's global dictionary-attack lockout ([systemd-cryptenroll(1)](https://man.archlinux.org/man/systemd-cryptenroll.1)).
- It is the oddlama article's primary mitigation.
- On a handheld it means typing a PIN on every cold boot: on the detachable keyboard, or on a touch keyboard if you switch plymouth for unl0kr (A.4).
- Recommendation: offer it as an opt-in (`OXP3_TPM_PIN=1`). Keep the default PIN-less with Game Mode autologin.

### A.3 Idempotent procedure (Phase 1: SB off, PCR 7 + 15=0)

The script is built only on facts verified in v262 sources and man pages:
- **Listing slots.** `systemd-cryptenroll DEV` with no options lists slots (`list_enrolled()` in [cryptenroll.c v262](https://github.com/systemd/systemd/blob/v262/src/cryptenroll/cryptenroll.c)). For machine-readable state, use `cryptsetup luksDump --dump-json-metadata DEV` (LUKS2 only).
  - Token `type` is `systemd-tpm2`, with fields `keyslots`, `tpm2-pcrs` (array), `tpm2-pcr-bank`, `tpm2-pin`, `tpm2_pubkey_pcrs`, `tpm2_pcrlock` ([tpm2-util.c v262 ~L11321](https://github.com/systemd/systemd/blob/v262/src/shared/tpm2-util.c)).
  - The recovery key token is `systemd-recovery` ([cryptenroll-recovery.c](https://github.com/systemd/systemd/blob/v262/src/cryptenroll/cryptenroll-recovery.c)).
- **Non-interactive unlock for enrolment.** Three options:
  - The env var `PASSWORD` (`getenv_steal_erase("PASSWORD")` in [cryptenroll-password.c v262](https://github.com/systemd/systemd/blob/v262/src/cryptenroll/cryptenroll-password.c)).
  - `--unlock-key-file=PATH`. The file must contain only the key, so write it with `printf '%s'` and no newline.
  - Credential `cryptenroll.passphrase`.
  - `NEWPIN` is used for the TPM PIN ([cryptenroll-tpm2.c](https://github.com/systemd/systemd/blob/v262/src/cryptenroll/cryptenroll-tpm2.c)).
  - New in v262: `--unlock-empty` and `--unlock-headless`.
  - `--unlock-tpm2-device=auto` exists since v256, but **it will fail in the running system once PCR 15 is bound**, because PCR 15 is non-zero after the root volume is opened.
- **Replacing slots.** `--wipe-slot=tpm2` combined with `--tpm2-device=auto`: "the enrollment is completed first, and only when successful the wipe operation executed … the newly added slot is always excluded from the wiping."
- **Detecting a failed TPM unlock on the last boot.** systemd-cryptsetup logs `…falling back to traditional unlocking` ([cryptsetup.c v262](https://github.com/systemd/systemd/blob/v262/src/cryptsetup/cryptsetup.c), ~L1993–2130). Initrd logs are flushed into `journalctl -b`.

```bash
#!/usr/bin/env bash
# oxp3-tpm-enroll.sh — idempotent TPM2 enrolment for the root LUKS volume (Phase 1, SB off)
# Usage: sudo oxp3-tpm-enroll.sh            (prompts for passphrase once, only if work is needed)
#        PASSWORD=... sudo -E oxp3-tpm-enroll.sh   (unattended)
#        OXP3_FORCE=1 ...                   (re-enrol even if metadata looks right)
set -euo pipefail
UUID=<luks-uuid>
NAME=luks-$UUID
DEV=/dev/disk/by-uuid/$UUID
ZERO=$(printf '0%.0s' {1..64})
PCRS="7+15:sha256=$ZERO"                      # want: PCR7 current value, PCR15 must be all-zero
OPTS="tpm2-device=auto,tpm2-measure-pcr=yes,x-initrd.attach"
rebuild=0 need_enrol=0

# 0. never let the GM7 NVMe s2idle bug interrupt a LUKS header write
[[ ${OXP3_INHIBITED:-} ]] || exec systemd-inhibit --what=sleep:idle:handle-lid-switch \
     --why="LUKS enrolment" env OXP3_INHIBITED=1 "$0" "$@"
grep -qw 'nvme.noacpi=1' /proc/cmdline || echo "WARN: nvme.noacpi=1 not active (see §0)" >&2

# 1. crypttab: single line for $NAME with the wanted options (only rewrite when different)
want="$NAME UUID=$UUID none $OPTS"
if ! grep -qxF "$want" /etc/crypttab; then
  tmp=$(mktemp); awk -v n="$NAME" -v w="$want" '$1==n{print w; done=1; next} {print} END{if(!done) print w}' /etc/crypttab >"$tmp"
  install -m600 "$tmp" /etc/crypttab; rm -f "$tmp"; rebuild=1
fi

# 2. inspect LUKS2 tokens
meta=$(cryptsetup luksDump --dump-json-metadata "$DEV")
has_recovery=$(jq '[.tokens[]|select(.type=="systemd-recovery")]|length' <<<"$meta")
tpm_ok=$(jq --argjson want '[7,15]' '[.tokens[]|select(.type=="systemd-tpm2")
          |select((.["tpm2-pcrs"]|sort)==$want and (.["tpm2-pin"]//false)==false)]|length' <<<"$meta")
tpm_any=$(jq '[.tokens[]|select(.type=="systemd-tpm2")]|length' <<<"$meta")
fell_back=$(journalctl -b -o cat -u 'systemd-cryptsetup@*' 2>/dev/null | grep -c 'falling back to traditional unlocking' || true)
(( tpm_ok == 1 && tpm_any == 1 && fell_back == 0 )) || need_enrol=1
[[ ${OXP3_FORCE:-} ]] && need_enrol=1

# 3. get the passphrase once (env PASSWORD wins; never written to disk)
if (( need_enrol || has_recovery == 0 )) && [[ -z ${PASSWORD:-} ]]; then
  read -rsp "Current LUKS passphrase: " PASSWORD; echo; export PASSWORD
fi

# 4. recovery key (only if none) — printed once on stderr: the user MUST record it
if (( has_recovery == 0 )); then
  PASSWORD="$PASSWORD" systemd-cryptenroll "$DEV" --recovery-key
fi

# 5. (re-)enrol TPM2, atomically replacing any old TPM2 slots
if (( need_enrol )); then
  PASSWORD="$PASSWORD" systemd-cryptenroll "$DEV" --tpm2-device=auto --tpm2-pcrs="$PCRS" --wipe-slot=tpm2
fi
unset PASSWORD

# 6. initramfs (only when crypttab changed)
(( rebuild )) && mkinitcpio -P
lsinitcpio "/boot/initramfs-linux-cachyos-deckify.img" | grep -qx 'etc/crypttab' \
  || { echo "ERROR: crypttab not in initramfs" >&2; exit 1; }
systemd-cryptenroll "$DEV"     # final listing for the log
```

Notes:
- The `PASSWORD` env var is consumed and erased by each `systemd-cryptenroll` process ("steal_erase"), which is why it is re-passed explicitly. Using `--unlock-key-file=/run/…` on a tmpfs is the alternative.
- **After the next boot, verify:**
  - `systemd-analyze pcrs 15` is non-zero, which proves `tpm2-measure-pcr=yes` ran in the initrd.
  - `journalctl -b -u 'systemd-cryptsetup@*'` has no "falling back" line.
- **After any PCR 7 change** (SB on, BIOS update, dbx update), boot once with the passphrase and re-run the script. The journal check triggers re-enrolment automatically.
- **Phase 2** (SB + UKI):
  1. Fill `/etc/kernel/cmdline`. Its current content uses `rd.luks.uuid` and `root=/dev/mapper/…`, which is fine. Add `nvme.noacpi=1`.
  2. Set `default_uki="/boot/EFI/Linux/cachyos-deckify.efi"` in the preset and install `systemd-ukify`.
  3. Stop sdboot-manage generating Type #1 entries.
  4. Run `sbctl create-keys` and `sbctl enroll-keys -m`, then sign sd-boot (`-s -o …efi.signed`), then `bootctl update`.
  5. Enable SB in the BIOS, boot with the passphrase once, then `OXP3_FORCE=1` re-run the same script. The PCR set stays `7+15=0`.

### A.4 Plymouth / no-keyboard UX

- **When the TPM unseals**, no prompt appears: plymouth goes straight to the splash.
- **When it fails**, systemd-cryptsetup asks via the ask-password agent. Plymouth renders the prompt.
- **crypttab defaults:** `timeout=` is 0 (wait forever), `tries=` is 3, and `token-timeout=` is 30 s, which only covers waiting for the TPM to *appear*, irrelevant with built-in CRB ([crypttab(5)](https://man.archlinux.org/man/crypttab.5)).
  - So with no keyboard attached, the device sits at the prompt indefinitely. Leave the defaults; a timeout would only drop to emergency mode.
- **Keyboards in the initrd.**
  - The detachable keyboard is a USB HID (`Juer Xin Keyboard K2445`, usb 3-6, per `/proc/bus/input/devices`).
  - The `keyboard` hook always adds `usbhid`, and `sd-encrypt` adds `hid-generic`, so it works in the initrd even though `keyboard` runs after `autodetect` (see `/usr/lib/initcpio/install/keyboard`).
  - Bluetooth keyboards do not work there.
- **No on-screen keyboard in plymouth.** No plymouth OSK was found. The community route is **unl0kr** (postmarketOS buffybox), which replaces plymouth:
  - Guides: [CachyOS handheld guide, 2025-12-25](https://discuss.cachyos.org/t/guide-luks-touchscreen-on-steam-deck-running-cachyos-handheld-edition-unl0kr/20293) and [CachyOS forum thread 26389 (2026-04)](https://discuss.cachyos.org/t/cannot-enter-luks-encryption-password-without-a-physical-keyboard/26389).
  - Package: [AUR `unl0kr`](https://aur.archlinux.org/packages/unl0kr). Upstream has a systemd `unl0kr-agent` ([buffybox/unl0kr](https://gitlab.postmarketos.org/postmarketOS/buffybox/-/tree/master/unl0kr)).
  - The OXP3 touchscreen is a Goodix I2C-HID (`GXTP6933:00 27C6:0133`), so it would need `i2c_hid_acpi hid_multitouch` in `MODULES=`.
  - The guide's `cp /etc/crypttab /etc/crypttab.initramfs` step is now deprecated (A.1).
  - Treat unl0kr as optional. It is only needed if TPM-with-PIN is chosen, or for touch-only recovery.

## B. Fingerprint (ACPI BF63112)

### B.1 Identification (device evidence + sources)

- **sysfs and ACPI nodes.** sysfs has `/sys/bus/spi/devices/spi-BF63112:00` → `\_SB_.PC00.SPI1.FPRT` on `pxa2xx-spi.6`/`spi1` (LPSS SPI, PCI 00:1e.3), with `modalias acpi:BF63112:`. It has **no driver bound**, and its SPI statistics are all 0.
  - A second ACPI node, `BF63112:01` = `\_SB_.PC00.SPI2.FPRT`, has `_STA` 0x0F but no SPI device enumerates under it. That is the "appears twice" in ACPI.
  - SPI2's `_INI` does not set the GPIO numbers (`LDGP`/`LRGP`), so it looks like a BIOS template copy.
- **DSDT** (`iasl -d`, `Scope (_SB.PC00.SPI1) Device (FPRT)`):
  - `SpiSerialBusV2 (0x0000 /*CS0*/, PolarityLow, FourWireMode, 8 bit, ControllerInitiated, 0x003D0900 /*4 MHz*/, ClockPolarityLow, ClockPhaseFirst /*mode 0*/, "\\_SB.PC00.SPI1")`
  - `GpioInt (Edge, ActiveHigh, ExclusiveAndWake, …, "\\_SB.GPI1")`, with the pin from `LDGP = 0x001A0412`. This maps to **GPP_F_18**: debugfs `pin 18 (GPP_F_18) … INTC10BC:01 … 0x82100100`, RX enabled.
  - `GpioIo (Exclusive, PullUp, …, IoRestrictionOutputOnly, "\\_SB.GPI1")`, with the pin from `LRGP = 0x001A0410`. This maps to **GPP_F_16**: debugfs `pin 16 (GPP_F_16) … 0x84000201 [LOCKED, ACPI]`, TX-only and driven high.
  - This is consistent with the sensor being **held in reset (active-high)** by firmware, as the community driver reports.
  - There is no `_DSD`/`_DSM`. `\_SB.GPI1` = `INTC10BC:01`.
- **Vendor.** "BF" is **Betterlife / BLESTECH** (Shenzhen/Chengdu Betterlife Electronic Technology).
  - Windows names the device "Betterlife Fingerprint Device/Reader" ([oemdrivers ACPI\BF63112](https://oemdrivers.com/devid/acpi-bf63112), [driverpack](https://driverpack.io/en/hwids/ACPI%5CBF63112?os=windows-10-x64)).
  - Related IDs: `ACPI\BF61100`, `ACPI\BF63100`, and USB VID `347D`.
  - Windows INFs: `betterlifefingerprintdevice.inf` and `betterlifemocwbdi.inf` ([driver-fusion DB](https://treexy.com/products/driver-fusion/database/biometrics/blestech/betterlife-fingerprint/), secondary source, medium confidence).
- **Sensor.** Chip ID **0x6683**, a 64×80 px image, match-on-host. The family includes 0x5f83 (96×112) and 0x6583 (88×100) ([pythontyphon/oxp3-fingerprint-linux README](https://github.com/pythontyphon/oxp3-fingerprint-linux), [driver fork](https://github.com/pythontyphon/libfprint-bf63112-oxp3), branch `oxp3-bf63112`).
  - Confidence: high on vendor and interface, medium-high on chip ID (taken from the fork, not independently read).

### B.2 Linux support status (as of 2026-10-07)

- **Upstream libfprint:** **unsupported.**
  - Latest release is 1.94.100 (2026-07-25); fprintd's latest is 1.94.5 ([libfprint releases](https://gitlab.freedesktop.org/libfprint/libfprint/-/releases), [fprintd releases](https://gitlab.freedesktop.org/libfprint/fprintd/-/releases)).
  - The only SPI driver is `elanspi`, which pairs ELAN7001/ELAN70A1 ACPI IDs with an Elan touchpad HID ([drivers tree](https://gitlab.freedesktop.org/libfprint/libfprint/-/tree/master/libfprint/drivers), [elanspi.h](https://gitlab.freedesktop.org/libfprint/libfprint/-/blob/master/libfprint/drivers/elanspi.h)).
  - Upstream issue [#793 "Unsupported SPI Fingerprint Scanner: Betterlife/BLESTECH (ACPI: BF63112)"](https://gitlab.freedesktop.org/libfprint/libfprint/-/work_items/793) was opened 2026-04-14 and closed 2026-07-02 as "Driver Request".
  - BF63112 is listed under [Unsupported Devices → SPI](https://gitlab.freedesktop.org/libfprint/wiki/-/wikis/Unsupported-Devices).
  - No MR exists. Arch `extra/libfprint 1.94.100` and the CachyOS rebuild do not include it ([archlinux.org](https://archlinux.org/packages/extra/x86_64/libfprint/), [packages.cachyos.org](https://packages.cachyos.org/?search=libfprint)).
- **Kernel:** no driver. The design is userspace over `spidev`.
  - `spidev_acpi_ids` only lists `SPT0001–3` ([spidev.c](https://github.com/torvalds/linux/blob/master/drivers/spi/spidev.c)), so binding needs `driver_override`. libfprint's own generated udev rules do the same for elanspi ([fprint-list-udev-rules.c](https://gitlab.freedesktop.org/libfprint/libfprint/-/blob/master/libfprint/fprint-list-udev-rules.c)).
  - `CONFIG_SPI_SPIDEV=m` and `CONFIG_SPI_PXA2XX=m` are present in the CachyOS kernel.
- **Community, newest first:**
  - [pythontyphon/oxp3-fingerprint-linux v0.1.0 (2026-09-25)](https://github.com/pythontyphon/oxp3-fingerprint-linux/releases/tag/v0.1.0) plus [libfprint-bf63112-oxp3](https://github.com/pythontyphon/libfprint-bf63112-oxp3), which is libfprint 1.94.100 plus 8 commits.
    - It is **targeted at the OXP3 with BIOS 5.09**.
    - Matching uses open SIGFM (SIFT/OpenCV) plus RANSAC, with no blobs.
    - Results: ~7/10 first-touch matches, 0/30 false accepts, 8–25 touches to enrol.
    - The KDE lock screen was tested. Suspend/resume, sudo and GNOME were not.
    - Prebuilt only for Fedora 44; `build.sh` builds inside a Fedora podman container.
    - Install footprint: `/usr/local/lib64/libfprint-bf63112/` plus a fprintd drop-in (`LD_LIBRARY_PATH`, `DeviceAllow=char-gpiochip rw`). The [udev rule](https://github.com/pythontyphon/oxp3-fingerprint-linux/blob/main/69-libfprint-bf63112.rules) binds spidev and sets `LIBFPRINT_BF63112_RESET_GPIO="INTC10BC:01 16 active-high"` matched on DMI ONE-NETBOOK / ONEXPLAYER 3. It also sets `spidev bufsiz=16384`.
    - The GPIO line matches the DSDT and debugfs evidence above.
    - The repo is brand-new and unreviewed: 0 stars, and the commits are co-authored by an AI assistant.
  - [dedbin/libfprint-bf63112](https://github.com/dedbin/libfprint-bf63112) (2026-07-22): the earlier driver. Matching needs the proprietary Windows `BetterlifeEngineAdapter.dll` run under Wine, and it was tested only on chip 0x5f83. Not suitable.
  - There is no AUR package (searches for "bf63112" and "betterlife" return 0 results).

### B.3 What it would take on CachyOS, and the PAM layout

**Verdict: not supported by any distro package. Experimental support is achievable with a native Arch build of the fork.**

What that build needs:
- `meson -Ddrivers=…,bf63112` (it is not included in `all`), plus the `opencv` package. Install under `/usr/local/lib/libfprint-bf63112`.
- The upstream `fprintd` package, with the fork's drop-in, udev and modprobe files.
- Reading from SPI binds `spidev`, so do it only after a reviewed install. It cannot be tested read-only.

If adopted, PAM changes are as follows. The service file names were verified, the edits were not tested:
- **KDE lock screen:** Arch kscreenlocker already ships `/usr/lib/pam.d/kde-fingerprint` with `-auth required pam_fprintd.so`, so no edit is needed ([kde-fingerprint.pam](https://gitlab.archlinux.org/archlinux/packaging/packages/kscreenlocker/-/blob/main/kde-fingerprint.pam), [kscreenlocker README.pam](https://invent.kde.org/plasma/kscreenlocker/-/blob/master/README.pam)).
- **plasmalogin:**
  - Its Arch PAM files are `plasmalogin`, `plasmalogin-autologin` and `plasmalogin-greeter` ([invent](https://invent.kde.org/plasma/plasma-login-manager/-/tree/master/data/pam/arch)).
  - The device currently **autologins** into `gamescope-session.desktop` (`[Autologin] User=<user> Relogin=true` in `/etc/plasmalogin.conf.d/`), so greeter fingerprint is moot.
- **sudo / polkit:** adding `auth sufficient pam_fprintd.so` to `/etc/pam.d/sudo` (or `system-auth`, which polkit-1 also includes) is possible.
  - With a ~70 % first-touch matcher, a 3-try fprintd prompt before the password is irritating. Not recommended.
- **KWallet:** `pam_kwallet5` can only open `kdewallet` with the login *password*. Fingerprint logins and autologin give it none ([Arch Wiki KDE Wallet](https://wiki.archlinux.org/title/KDE_Wallet), [KDE discuss thread](https://discuss.kde.org/t/plasma-login-manager-fingerprint-extra-unlock-step-and-kwallet-behavior/43840)).
  - With FDE plus autologin, the usual choice is an empty wallet password: data at rest is still covered by LUKS.
- **Steam Game Mode:** gamescope-session has no PAM lock screen. Steam's own lock PIN is internal to the Steam client (unverified, low confidence), so fingerprint plays no role there.

**Alternatives if you skip the fork:** TPM unlock plus autologin (C), the lock-screen password, or a short lock-screen password and no wallet password.

## C. Combined recommendation

1. **Fix the NVMe resume bug first** (`nvme.noacpi=1`, §0).
2. **Phase 1, now.** Run the idempotent script in A.3:
   - TPM2 bound to PCR 7 plus PCR 15=0, with `tpm2-measure-pcr=yes,x-initrd.attach` in `/etc/crypttab`.
   - Keep the passphrase (slot 0) and add a recovery key, recorded off-device.
   - Be explicit with the user that with Secure Boot off this is convenience. It protects an SSD removed from the device, not a stolen device.
3. **Phase 2, recommended.** Secure Boot with own keys via sbctl (with `-m`), signed systemd-boot, and a mkinitcpio UKI. Retire sdboot-manage's Type #1 entry. Re-enrol with the same PCR set.
   - This gives real theft protection with no friction from kernel updates.
   - Optional extras: ukify-signed PCR 11 policy; a BIOS supervisor password so SB cannot be silently disabled (that is detected anyway, since PCR 7 changes and you get the passphrase prompt).
4. **Session model.**
   - Autologin into Game Mode, as already configured.
   - In Desktop Mode, auto-lock the screen on resume and idle, unlocked by password (plus fingerprint only if the fork is adopted).
   - sudo and polkit stay password-only.
   - Use an empty KWallet password, or accept the wallet prompt.
   - This mirrors SteamOS-style convenience while keeping the disk sealed to this machine's boot chain.
5. **Opt-in high security.** `--tpm2-with-pin=yes` plus unl0kr touch keyboard, for users who carry the device outside the home.
